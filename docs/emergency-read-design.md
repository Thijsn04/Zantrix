# Emergency read contract and independent reader design

Date: 15 October 2026. Status: Accepted architectural direction and production requirements (R135–R142), following the owner's explicit approval and four technical refinements. Exact schemas, operational/security profiles and runtime proof remain open. No reader, validator, exporter or audit pipeline is implemented. Keep documentation local until explicitly requested to commit/push.

## Fixed boundary and independence

Preserve the [existing continuity requirements](continuity.md): local read-only emergency access for managed and self-hosted installations, the full-record coverage goal, a maximum five-minute lag target under healthy connectivity, independent authentication/authorization, encryption/protected keys, local audit and truthful age/completeness indicators. The target is not a measured SLA or backup recovery point objective. Dataset exceptions, site selection, identity/key mechanisms, RTO/RPO and hardware remain Open.

Use a standalone local reader with its own protected storage and a deliberately limited rendering runtime. It reads standardized, versioned projections/documents; it must not execute clinical module JARs, module-supplied React bundles or arbitrary module renderers. Reader technology and database are not selected. A main-app module failure must not inherently require that module to run in the reader, but shared libraries, infrastructure, corrupted data and endpoint failures can still create common failure paths. Independence needs evidence, not an absolute availability claim.

The reader must work without live primary Core/Bridge/database, online session store, broker or unavailable upstream IdP. Offline access cannot promise instant knowledge of central revocation or enforce a globally single active workspace across a partition. Offline authority, expiry, emergency exceptions and local administration require a separate reviewed profile; outage alone does not grant everyone unrestricted patient access.

Read-only refers to clinical state: no prescribing, orders, clinical editing or automatic clinical write-back. The reader necessarily writes controlled local synchronization metadata and audit records. Care delivered during downtime uses a separate documentation/reconciliation procedure; importing audit events later is not reconciliation of those clinical notes.

## Mandatory classification and production gate

Every module declares `clinicalDataClassification` in its manifest, with the accepted values `PERSISTENT_DOSSIER_OWNER` or `NON_DOSSIER_TRANSIENT`. The latter means no owned persistent patient/dossier data; it does not prohibit ordinary non-patient technical configuration. No exemption follows simply from calling a module an adapter, cache or workflow helper.

Any module owning patient-bound database tables requires a registered, versioned, working and tested `EmergencyReadContract` by default. Classification checks must also examine durable file/object storage, migrations, data contracts and actual owned data; moving information outside SQL cannot bypass the requirement. A claimed `NON_DOSSIER_TRANSIENT` exemption requires evidence that no such patient-bound persistence is owned, including durable workflow status where applicable. Shared technical outbox/audit storage and payload retention need explicit ownership/coverage treatment, not an implicit technical-module waiver.

Staging validates classification, owned storage, contract/reader compatibility, declared coverage and conformance evidence for the exact version/deployment combination. Static scans alone do not prove the absence of persistence or sandbox arbitrary same-process code. The detailed evidence/admission pipeline remains Open.

No production activation without a validated emergency contract or a proven applicable exemption. Apply the gate to official, external and locally installed packages and to updates changing coverage or projection versions. Local/unreviewed installation is not a bypass. This requirement selects a production condition, not clinical certification or guaranteed completeness of arbitrary data.

Activation must register the expected owner/coverage entry with each required site reader and verify initial baseline/no-data coverage and compatible rendering before the new owner can silently introduce an unknown gap. The enrollment/activation protocol and exact required-site set remain Open. A later runtime synchronization failure must become visible and actionable; it does not silently deactivate an already operating clinical module or select a new automatic-shutdown policy.

## Versioned projection and human-readable baseline

An Emergency Read Contract defines exported record types, authoritative owner, patient/care identifiers, supported projection versions, provenance, status/corrections/history, related references, attachments and declared coverage/limitations. Each projection has a bounded typed schema and a standardized human-readable basis, such as sections, tables or timeline items. Specialized online interaction is not required in the reader. An arbitrary JSON blob that only the original module can interpret is insufficient.

Clinical content such as units, times, status, cancellations and corrections must remain interpretable; a static chart without essential meaning or source context is not automatically a usable fallback. Generated PDFs/images can supplement the baseline, with accessibility/search requirements and clinical review appropriate to their content. Exact standard primitives, supported formats and first-release coverage remain Open. The aim of full-record access does not settle medical imaging, external attachments or complete resource-history handling.

All required content must be locally available within the declared coverage. An external URL is a missing dependency during a network outage, not proof that a document was copied. Preserve authoritative patient identity/merge relationships and links within the exported dataset. Represent omissions, unsupported versions and inaccessible attachments explicitly; never turn them into an empty clinical section.

Treat projections and pre-rendered files as untrusted input: validate bounded schemas, sizes, content types, references and integrity/provenance; exclude active scripts, embedded actions and uncontrolled network dependencies. The [SVG processing-mode specification](https://www.w3.org/TR/SVG2/conform.html#secure-static-mode) distinguishes restricted processing from active content. Merely naming a file SVG/PDF or sanitizing its extension does not establish passive rendering. Exact safe renderer/format policy requires proof; the reader cannot depend on downloaded module code or a live rendering service.

Module retirement/update must preserve compatible rendering of retained projections or a validated conversion, without restoring retired module execution. This supports emergency readability but does not replace the ordinary archive/exit route or prove all historical data was retained.

## Durable change trigger and projection generation

Use the accepted transactional outbox from R116 and original-context rules from R117. Every covered clinical change commits its required projection-update obligation in the same business transaction; a rollback produces no committed obligation. Perform heavy projection generation and transport asynchronously afterward under current scoped service/workflow authority (R123), not a surviving human session. Existing [transaction/outbox requirements](core-bridge-data-design.md#accepted-durable-follow-up-direction) remain authoritative; the storage layout in R119 remains Proposed.

Events identify the affected patient/owner scope and committed source revision or equivalent change frontier. Projection generation runs on the primary side through owner contracts; no cross-owner SQL joins or reader-side module execution are introduced. A later read of current state may include additional changes: it must truthfully identify what was captured, not label current data as the exact historical state of an earlier event. The [PostgreSQL isolation documentation](https://www.postgresql.org/docs/current/transaction-iso.html) explains why successive reads under Read Committed need not share one snapshot; snapshot/cutoff construction across owner contracts remains to be specified.

Provide initial bulk baselines, retries, idempotent delivery, reconciliation and recovery for missed/failed work. Incremental outbox triggers avoid mandatory repeated full-dossier scans for every edit; they do not eliminate all scans or prove the five-minute target without load/large-document tests. If triggers are coalesced, preserve their covered revision frontier and required history/corrections. Explicitly handle patient merges, transfers, restricted/deleted content under retention policy and retired owners rather than dropping them as ordinary missing rows.

## Atomic installation and consistency boundaries

Packages carry patient/owner identity, schema/rendering version, source revision/frontier, stable package identity, integrity hash, sequence/epoch and attachment manifest. Checksums detect corruption relative to trusted expected values; authentic producer/device binding needs protected transport/signing or an equivalent trust mechanism. No algorithm, key hierarchy or transport has been chosen.

The reader stages and validates the complete package and its required files locally, makes it durable, then atomically publishes the new active revision and matching metadata. Incomplete or incompatible packages retain the last validated revision with a visible failure/coverage warning. Acknowledgement means durable installation, not receipt in RAM. Crashes, disk-full conditions, duplicate/out-of-order delivery, replay, retries and storage recovery must not regress an active revision or expose partial contents. Sequence alone is insufficient if generations reset; define epochs and restart/migration rules. Exact local storage/atomicity mechanism remains Open.

Per-component atomic replacement does not establish a consistent whole dossier. Related changes within one source transaction, or a declared cross-owner dependency group, need a coverage/consistency frontier before the reader can claim a complete coherent view. Retain a validated common cutoff where supported, or show explicit mixed-age/incomplete status when components are not aligned. Do not present a fresh medication section plus a missing related allergy update as a coherent current dossier. Two distinct clinical commits may legitimately be observed at a cutoff between them; the reader must not invent that they were one atomic clinical operation.

The exact barrier/group protocol remains Open. There is no universal equal version N across independent module counters, and a database sequence, timestamp or highest received event ID alone is not proof that all earlier committed changes have arrived. Prove contiguous coverage with commit/dependency semantics and gap handling before advertising an all-owner cutoff.

## Per-patient coverage and freshness watermarks

Maintain an independently known registry of expected active and retained owners and their declared dataset/site scope. The reader must know that a module is missing, even when that module has never successfully delivered a package. Offline knowledge cannot include a deployment change never communicated to that reader; activation/enrollment must address this boundary.

Expose both system-level verified coverage and per-patient/per-owner status. Distinguish transport heartbeat/last contact, package capture time, source changes covered through a verified frontier, durable installation time and the last clinical modification. A quiet record can be covered through a recent verified checkpoint without being regenerated simply to change its modification time. A successful ping cannot advance a data-coverage watermark.

The global last complete system checkpoint is shown only when all expected data within the explicitly declared scope is verified through that cutoff. It is not the newest successful module timestamp or last successful download. If no global complete checkpoint is established, say unknown/incomplete and show individual available coverage. A patient-specific view can have a different verified frontier from the global baseline.

For each patient and expected owner, distinguish verified data, verified no applicable records, outside declared site scope, never received/unknown, failed/incomplete, incompatible and stale. Absence is not an empty negative clinical finding. Show missing-owner/content warnings in the relevant section and a dossier-wide summary with age and provenance. Completeness, consistency and freshness are separate dimensions: complete old data is still old; fresh delivery of an incomplete subset is still incomplete. A positive status requires evidence across all applicable owners and no unresolved gaps.

The five-minute healthy-connectivity target concerns verified source coverage through durable readable installation, not just event enqueue or network receipt. Monitor build/queue/transfer/install lag, failed content and gaps, with operator escalation and realistic clock/ordering handling. During outage, preserve readable verified data while displaying its increasing age and limitations. This neither guarantees zero loss of primary data nor replaces backups/restoration evidence.

## Independent audit and recovery reconciliation

Maintain a local append-only, cryptographically hash-chained access log under an explicit device/instance identity. Record actual authenticated actor, relevant patient/resource, purpose/exception, access outcome, local sequence/event identity, time/clock quality and the data revision/coverage seen. Minimize sensitive payloads; do not copy dossier contents or reusable credentials into logs. Emergency access is not automatically weaker authentication or unreviewed break-glass.

Hash chaining makes particular changes detectable relative to a trusted chain state; it cannot alone prevent a privileged attacker rewriting the full chain or prove missing/truncated events never existed. Protect keys/storage and anchor chain heads through a defined trusted mechanism when possible, with offline integrity limits. [OWASP's logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) calls for protected logs and detection of tampering, modification and deletion. Exact anchoring, retention, access review and behavior on audit-storage failure remain Open. Do not claim 100% audit completeness or NEN 7510 compliance from this mechanism.

After recovery, authenticate the reader to the primary audit-ingestion contract, verify device/sequence/chain continuity, deduplicate stable event identities, retain original actor/time/context and separately record ingestion time/identity. Treat events as external evidence, not current authority or a reason to impersonate a staff member. Acknowledge durable acceptance and retry safely; preserve local evidence until the agreed retention/acknowledgement policy permits removal. Missing/corrupt ranges, ambiguous clocks and conflicting identities require visible investigation, not invented continuity. Primary audit ingestion through Core's technical contract must respect the agreed authorization/ownership boundary.

No automatic clinical merges arise from reader access, because the reader does not edit clinical state. Separate downtime documentation may still require clinically reviewed reconciliation. Primary recovery does not erase the reader's evidence, automatically resolve gaps or silently grant broader offline privileges.

## Proof obligations and remaining design

Before product implementation, specify classification evidence, typed projection/format versions, expected-owner registry/enrollment, snapshot cutoff/group semantics, package authenticity/atomic durable publication, watermarks, independent offline authority/keys and audit anchoring/ingestion. Keep exact algorithms, deployment topology and thresholds Open until reviewed.

A later authorized synthetic proof must cover production rejection without contract/exemption, false transient claims, both install routes, initial patient/module enrollment and reader-version incompatibility. Disable all live primary identity/data services and verify declared data remains readable without module execution. Test specialized-data fallback, missing attachments, unknown owners versus empty sections, corrupted/active-content packages, mixed-owner revisions, deletion/correction/merge semantics and retained data after module removal.

Exercise interruption/crash/disk-full during package installation, acknowledgement loss, duplicate/reordered events, projection failure/large datasets and measured five-minute source-coverage lag under defined healthy conditions. Test offline authorization expiry/revocation limits, read audit, tampering/truncation detection limits, audit-storage failure and duplicate/interrupted recovery ingestion. Backup/restore and RTO/RPO tests are separate. No such proofs or compliance assessments have been performed.
