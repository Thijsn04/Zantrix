Immediate instruction for a new assistant
Continue as an architecture and product-design collaborator.
The owner wants to rebuild Zantrix as a mature, open-source, modular EHR that can eventually be used in real clinical care.
Do not start implementing the application merely because this handover contains extensive requirements. Requirements discovery and detailed architecture design are still ongoing.
The owner has explicitly requested:
1. A full rebuild rather than continuing to patch the old application.
2. Preservation of all design decisions.
3. Continued questions to thoroughly understand the product.
4. Documentation updates in batches of approximately ten answered questions, rather than filesystem work after every answer.
5. All accumulated work to be written to the repository.
6. Commit and push of that work once repository access is available.
The permission to commit and push is already present. Do not request that same permission again merely because the session changed.
Before writing or pushing:
- Inspect the actual repository, branch, remote state and local changes.
- Preserve recovered work.
- Read any current AGENTS.md.
- Determine whether the previous documentation rebuild survived.
- Merge recovered files and this handover carefully.
- Do not reset, overwrite or delete unknown local changes.
- Do not assume master still points to the previously observed commit.
- Do not force-push.
- Respect any branch protections.
- Verify the actual pushed commit and report its SHA and branch.
Status vocabulary
Use these distinctions consistently:
- Agreed: an explicitly accepted requirement or architectural direction.
- Provisional: an expressed preference that still needs confirmation or validation.
- Proposed: an assistant recommendation that has not been fully accepted.
- Open: a decision still required.
- Implemented: supported by current code and verification.
- Superseded: replaced by a later decision.
Most material in this handover is design, not implemented functionality.
Do not equate:
- Documentation with implementation.
- A passing build with a clinically usable product.
- Automated tests with certification.
- Local file writes with a GitHub push.
- A saved environment draft with publication or filesystem recovery.
Interaction style
The owner wants a collaborative discussion with many useful questions over time.
Prefer:
- One substantive main question at a time.
- Concrete alternatives and a recommendation.
- Explanations when the owner asks why a decision matters.
- Explicit separation of technical mechanisms from product requirements.
- Periodic summaries and documentation checkpoints.
Avoid:
- Repeatedly asking already answered questions.
- Treating every assistant proposal as accepted.
- Prematurely selecting technologies or implementation details that remain open.
- Excessive tool work after each short answer.
- Building a generic framework before proving representative clinical workflows.
Existing design process
The discussion used an architectural brainstorming approach:
1. Understand the intended clinical product.
2. Establish scope and constraints.
3. Compare approaches.
4. Review architectural sections.
5. Consolidate a written design.
6. Review that written design.
7. Produce scoped implementation plans.
8. Implement and verify incrementally.
The owner accepted a first Core–Bridge module-contract outline. Detailed API design, implementation plans and product implementation have not been completed.

Document 2 — Product vision, scope and boundaries
Suggested path: docs/product.md
Vision
Zantrix is intended to become:
- A fully open-source modular electronic health record.
- Clinically usable after the necessary validation, operational work and applicable regulatory obligations.
- Suitable over time for different countries and care settings.
- A strong example of meaningful interoperability between medical systems.
- Maintainable by an open-source community rather than dependent on undocumented knowledge.
The owner does not want a superficial demonstration with many nominal features that do not form coherent clinical workflows.
Initial care setting
The first care setting is general practice.
The first country is the Netherlands.
The first deployable Dutch GP version is intended to fully replace an existing huisartsinformatiesysteem, or HIS.
It is not intended merely as a supplementary tool beside an existing HIS.
However, the first engineering milestone is smaller than a full replacement release.
First engineering milestone
Build one complete GP consultation workflow:
1. Find and select the patient.
2. Open the relevant appointment or care contact.
3. Review relevant existing information.
4. Record findings.
5. Determine and document the plan.
6. Complete or finalize the consultation appropriately.
This milestone must exercise the architecture, not just demonstrate isolated forms.
It should include the relevant foundations for:
- Correct patient context.
- Draft preservation.
- Finalization and corrections.
- Authorization.
- Safe editing.
- Shared UI.
- Synthetic scenarios.
A complete consultation milestone does not establish:
- Full HIS replacement.
- Production readiness.
- Clinical deployment approval.
- Completion of all required integrations.
Full HIS replacement
The eventual deployable scope must account for the actual practice's complete work.
Potentially necessary areas include:
- Clinical record workflows.
- Medication workflows and prescribing.
- Diagnostics and results.
- Correspondence and referrals.
- Scheduling.
- Practice administration.
- Required national integrations.
- Patient access.
- Migration from the previous HIS.
- Operational continuity.
- Security, privacy and clinical assurance.
The exact inventory must be established with the first practice. These examples are not a completed functional specification.
POH and POH-GGZ
Support for practice nurses, chronic-care workflows and POH-GGZ is an eventual goal.
Whether these are required in the first deployable release is unresolved.
The first practice's actual workflows determine whether the absence of those capabilities would prevent replacement.
International foundation
Do not embed Dutch requirements in the universal Core.
The architecture must distinguish:
- Shared technical foundations.
- Shared clinical capabilities.
- Care-setting workflows.
- Country-specific requirements.
- Language and localization.
National identifiers, exchange profiles, terminology requirements, connectors and applicable rules belong in appropriate country modules or adapters.
Care-setting modules
General practice must be a separate care-setting module.
Other future examples include:
- Hospital care.
- Mental-health care.
- Other specialist or institutional settings.
Care-setting modules compose shared capabilities into suitable workflows and workspaces.
They must not duplicate the underlying patient identity or create competing authoritative records merely because they provide another interface.
Multiple locations and care settings
One organization must be able to have:
- Multiple locations.
- Staff working across locations.
- Multiple care settings in the same installation.
Location-specific permissions and workflows are required.
The accepted patient-record direction is:
- One organization-wide patient identity.
- One coherent patient record across locations.
- Access governed by role, organization and care context.
Independent organizations and tenancy
A proposal was made to begin with one independent organization per installation.
The owner questioned the value of sharing an installation between independent organizations, since excellent interoperability should allow them to cooperate without sharing a system.
The benefits and costs of shared tenancy were explained.
However, the one-organization-per-installation proposal was not explicitly finalized as a complete tenancy design.
Treat this as an unresolved architectural confirmation, not permission to implement arbitrary multi-tenancy.
Hosting models
Support both:
Zantrix-managed hosting
Zantrix can provide hosting and technical management.
The owner expects the possibility of charging per enabled module for hosting/services.
Exact support commitments, service levels and operational responsibilities are not specified yet.
Self-hosting
Institutions can host and manage Zantrix themselves or through their own provider.
There is no direct support entitlement from Zantrix for self-hosted installations.
Self-hosters may still report bugs in official Zantrix modules.
Installation, updating, backup and restoration must be documented sufficiently for independent operation.
A mandatory dependency on a Zantrix-operated cloud control service has not been agreed.
Patient portal
An official patient portal should be developed as a separate module.
It is:
- Not inherently part of the Netherlands country module.
- Not required for the first engineering milestone.
- Not committed as an immediate first-version deliverable.
External patient portals must also be able to integrate through documented and authorized interfaces.
Portal features, patient identity, proxy access, guardianship and national sign-in mechanisms remain to be designed.
Public website
A separate public Zantrix website is required for:
- Product information.
- Promotion and project information.
- Documentation.
- Developer information.
- Possibly a future module catalog or marketplace.
Documentation should be applicable to specific releases.
No website technology, domain, hosting provider, visual design or publishing process has been selected.
Migration
Migration tools may be developed later, but the foundation must be ready for migration.
The design must support preservation of:
- Source-system identifiers.
- Provenance.
- Original authors and timestamps where available.
- Documents.
- Terminology.
- Clinical history and corrections.
Import validation, identity matching, duplicate assessment and reconciliation require explicit design.
A validated migration path is a prerequisite before an existing practice can actually replace its HIS.
Document 3 — Architecture and technology
Suggested path: docs/architecture.md
Chosen direction
The owner accepted the following technological direction:
- Java with Spring Boot for the backend.
- React with TypeScript for the frontend.
- PostgreSQL as the primary database.
- One repository for official project components.
- A modular monolith rather than separate services for every module.
- A uniform supported backend/frontend stack for external modules as well.
Exact versions and detailed libraries remain open.
Why Java rather than switching to C#/.NET
The owner has more experience with Java and TypeScript but explicitly asked for a serious comparison rather than choosing familiarity alone.
The comparison concluded:
- Java/Spring and C#/ASP.NET Core are both credible platforms.
- Both support mature transactions, security facilities, Linux hosting and PostgreSQL.
- Both have FHIR tooling.
- Neither language intrinsically makes an EHR clinically safe.
- Java experience reduces the initial maintainer's learning and code-review burden.
- Java has relevant architecture-verification tooling and healthcare ecosystem examples.
- No decisive requirement was identified that justified switching to .NET.
This was not based on a representative performance benchmark.
External projects examined
Public repositories and documentation were examined:
- OpenMRS: Java/Spring and an extension-module model.
- OpenMRS frontend: React/TypeScript ecosystem.
- OpenEMR: PHP-based EHR.
- EHRbase: Java/PostgreSQL openEHR data platform.
- HAPI FHIR: Java FHIR tooling.
- Firely SDK: .NET FHIR tooling.
- Spring Modulith and ArchUnit: module/architecture verification.
- .NET support policy.
References:
- https://github.com/openmrs/openmrs-core
- https://github.com/openmrs/openmrs-esm-core
- https://github.com/openemr/openemr
- https://github.com/ehrbase/ehrbase
- https://github.com/hapifhir/hapi-fhir
- https://github.com/FirelyTeam/firely-net-sdk
- https://github.com/spring-projects/spring-modulith
- https://github.com/TNG/ArchUnit
- https://github.com/dotnet/core/blob/main/release-policies.md
Some external websites were blocked by network policy.
The complete internal architectures of Epic and HiX were not verified. Do not invent claims about them.
Core, Bridge and Connect
These names are explicitly important.
Core
Core is the technical foundation.
Its proposed responsibilities include:
- Technical identity integration.
- Organizations and locations.
- Shared security facilities.
- Module lifecycle.
- Compatibility and configuration foundations.
Clinical capabilities should not automatically be put in Core.
Patient registration is a separate module.
Bridge
Bridge is the mandatory internal interaction component.
It connects Core and the different modules through standardized contracts.
It is not the external integration component.
It must not become:
- A duplicate store of every clinical record.
- A container for all clinical business logic.
- An untyped universal action dispatcher.
Connect
Connect handles external interoperability.
It provides or coordinates:
- Adapters.
- External communication.
- Standards mapping.
- Delivery state and failure handling.
- Country-specific connector implementations where applicable.
The initial terminology was different earlier in the discussion. The owner's correction supersedes that terminology:
Bridge = internal. Connect = external.

Module categories
The conceptual categories are:
1. Technical platform components.
2. Shared clinical modules.
3. Care-setting modules.
4. Country modules.
5. Shared user-interface platform.
6. External interoperability adapters.
7. Internal testing and synthetic-data facilities.
The final package boundaries are not selected.
One installation
Modules should initially run within one Zantrix installation.
The owner accepted one installation rather than designing every module as a separately deployed service.
This does not mean that:
- PostgreSQL must run in the same process.
- Every supporting service must be embedded.
- The emergency reader depends on the primary application.
- All interactions must become network calls.
Monorepo
Core, Bridge, Connect and official modules should be developed in one repository.
Benefits include:
- Coordinated cross-module changes.
- Shared tests.
- Consistent documentation.
- Easier development for one initial maintainer.
Modules still need explicit versions, interfaces and dependencies.
External developers can maintain their modules in separate repositories.
Versioning and installation
Separate module versioning is required.
However:
- Independently versioned modules are not necessarily independently hot-updatable.
- Supported combinations must be explicit.
- Incompatible combinations must be blocked.
- Required dependencies cannot be removed silently.
- Database migrations require controlled procedures.
Planned maintenance is acceptable.
Loading modules at controlled startup and restarting after updates was proposed. Hot replacement of clinical code was not required.
Data ownership
The accepted starting point is module-owned domain models.
For each authoritative datum:
- Assign one owner.
- Expose explicit contracts.
- Avoid direct writes to another module's tables.
- Avoid independently editable duplicate truth.
Copies may still be needed for:
- Backups.
- Emergency access.
- Derived views.
- Historical snapshots.
- External messages.
Such copies need explicit source, purpose, freshness and write-authority rules.
Clinical standards
The previous requirement that all internal clinical data must be stored as FHIR is superseded.
Nevertheless, existing clinical standards must be examined before inventing equivalents.
Relevant areas include:
- FHIR.
- openEHR.
- Identifiers.
- Terminology.
- Units.
- Provenance.
- Clinical versioning and correction semantics.
Connect cannot reconstruct meaning that the internal model did not retain.
Complexity limits
No current requirement mandates:
- Kubernetes.
- Microservices.
- Full event sourcing.
- A universal message broker.
- A custom network transport protocol.
- Dynamic hot replacement of clinical modules.
Introduce these only for a demonstrated need.
Trust boundary
Modules in one process are not security-isolated from each other.
Module boundaries, review and Bridge checks do not provide a sandbox against hostile installed code.
This limitation must be reflected in module governance and deployment policy.
Document 4 — Core–Bridge module contract
Suggested path: docs/module-contract.md
Status
The owner approved the contract outline below.
Exact classes, interfaces, schemas, package names and SDK signatures remain open.
Module manifest
Each module declares:
- Unique module identity.
- Module version.
- Supported platform-contract versions.
- Required dependencies.
- Optional dependencies.
- Supported dependency versions.
- Offered and consumed interfaces.
- Commands, queries and events.
- Required permissions.
- Configuration.
- Owned data.
- Data migrations.
- User-interface extension points.
- Localization contributions.
- Supporting services where required.
Core checks compatibility before installation and during startup.
Administrators should understand the consequences before enabling, updating, disabling or removing a module.
Queries
Queries request information without modifying clinical state.
Examples:
- Retrieve a patient's active medication list.
- Retrieve appointment information.
A query can still create an access-audit record.
Commands
Commands request an explicit state change.
Examples:
- Finalize a consultation note.
- Create a task.
- Request a diagnostic procedure.
Commands need defined:
- Preconditions.
- Permissions.
- Clinical invariants.
- Transaction boundaries.
- Concurrency behavior.
- Error outcomes.
- Repeat-request behavior.
Events
Events report facts that have already occurred.
Examples:
- A consultation note was finalized.
- A result was received.
- A task was completed.
An event is not an instruction to pretend an uncommitted change happened.
Typed contracts
Use explicit, typed and versioned contracts.
Do not make the public module API one generic function accepting arbitrary JSON and an action string.
Modules must be understandable and testable without reading each other's internals.
Synchronous and asynchronous work
Not every interaction should become asynchronous.
Use direct interactions when the caller needs an immediate authoritative result.
Use durable asynchronous processing when follow-up may occur later.
For asynchronous follow-up, a transactional outbox was proposed.
Detailed decisions remain open for:
- Delivery guarantees.
- Ordering.
- Retries.
- Deduplication.
- Dead-letter handling.
- Reconciliation.
Do not promise exactly-once delivery across independent external systems.
Transactions
Shared PostgreSQL does not automatically make cross-module operations safe.
Each operation must define what needs to succeed together.
Cross-module transaction participation requires explicit contracts.
Do not bypass ownership merely to obtain a convenient database transaction.
Request context
Interactions must carry and validate appropriate context, including:
- Authenticated human or service identity.
- Organization.
- Relevant patient.
- Relevant care context.
- Correlation and traceability.
Do not blindly trust actor names or patient IDs supplied by callers.
Authorization
Core supplies shared security facilities.
Bridge enforces relevant technical contract rules.
The owning module must still enforce:
- Domain permissions.
- Valid state transitions.
- Patient/context restrictions.
- Clinical invariants.
Background jobs, imports and external messages must not bypass these rules.
UI extension contract
Modules contribute screens, sections, tasks and actions through approved extension points.
They must use:
- Shared navigation.
- Shared patient workspace.
- Shared components.
- Shared validation and error conventions.
- Shared accessibility rules.
- Shared save-state behavior.
The frontend does not independently establish that an operation belongs to a particular patient. The server checks context.
Connect and incoming information
Separate:
1. Information received from another system.
2. Information assessed or adopted into the local clinical workflow.
Preserve source and meaning.
An incoming medication list must not silently overwrite the local active list.
Define handling for:
- Conflicts.
- Repeated delivery.
- Corrections.
- Retractions.
- Identity uncertainty.
- Operator review.
Standards may include FHIR, HL7 v2, DICOM and national profiles where concrete use cases require them. Supporting every standard is not an initial milestone commitment.
Document 5 — Clinical record, workspace and editing safety
Suggested path: docs/clinical-safety.md
Organization-wide record
A patient has one organizational identity and coherent record across locations.
Do not create separate competing records simply because the patient is seen at different sites or in different care settings.
Identity management
Design for:
- Duplicate detection.
- Identity matching.
- External identifiers.
- Merge.
- Recovery from an incorrect merge.
- Source-system provenance.
A matching identifier or demographic field must not automatically establish that two records belong to the same person.
Contacts, episodes and registrations
For GP care, combine:
- A timeline.
- Care contacts.
- Episodes or longitudinal problems.
- Individual clinical registrations.
One contact can address multiple problems.
An episode can span multiple contacts.
These are relationships and views over clinical facts, not instructions to duplicate the same note in multiple places.
Information must be able to await classification rather than requiring a fabricated diagnosis or episode.
Do not impose this exact GP workflow on every future institution.
SOEP
Support SOEP for appropriate GP documentation.
Do not put SOEP in universal Core.
Other countries and care settings must be able to use different documentation structures.
SOEP is not exclusively a Dutch concept; distinguish actual national requirements from broader clinical patterns.
One coherent user experience
The owner considers this extremely important.
Every module must feel native to Zantrix.
A shared visual style alone is insufficient.
Standardize:
- Navigation.
- Workspaces.
- Patient context.
- Forms.
- Validation.
- Messages.
- Errors.
- Accessibility.
- Terminology.
- Save behavior.
- Interaction patterns.
External modules must follow the same rules.
Epic was mentioned as a reference for multiple patient workspaces, not as a specification to copy wholesale.
Multiple patient workspaces
Support multiple simultaneously open patient records.
There must be a limit.
The exact number is not decided.
Requirements:
- Active patient clearly visible.
- Patient identity clear in dialogs.
- Workspace-specific care context.
- Isolated drafts.
- Pending requests bound to their original patient.
- No silent loss when closing a workspace.
- No unintentional context transfer when switching patients.
Drafts
Automatically save input as drafts.
Display truthful states such as:
- Saving.
- Saved.
- Save failed.
Autosave does not finalize or sign.
Restore drafts safely after refresh, interruption or session expiration.
Preserve:
- Patient.
- Author.
- Care context.
- Version.
Require appropriate authentication before accessing restored drafts.
Do not clear input merely because a request was started.
Finalization and corrections
Drafts may be editable.
Finalized clinical content must retain historical versions.
Use identifiable corrections or additions with:
- Author.
- Time.
- Reason.
- Relation to the previous content.
Other domains need their own lifecycle, such as stopping or replacing medication.
Concurrent work
Multiple users may view the same record.
Concurrent editing is allowed only where it is demonstrably safe.
The owner explicitly rejected uncontrolled editing of the same component.
Use:
- One editor per protected registration or workflow scope.
- A broader protected scope when independence cannot be established.
- Whole-record editing exclusion if necessary.
Example: medication-list changes may require broader protection than independent notes.
Lock takeover
Taking over editing requires an additional permission.
It is not a standard right for every clinician.
Requirements:
- Explicit reason.
- Audit.
- Preserve the existing draft.
- Reject stale writes from the original session.
- Provide safe handling of unsynchronized input.
Exact lease, heartbeat and expiry behavior remain open.
Duplicate prevention
Editing locks alone do not prevent duplicate data.
Also address:
- Double clicks.
- Retried requests.
- Repeated external messages.
- Sequential duplicate entry.
- Similar but clinically distinct facts.
Do not automatically merge superficially similar records.
Patient-level confidentiality
The owner selected initial restriction at patient level.
Separate confidentiality boundaries for individual notes or dossier components are not an initial requirement.
Roles still govern permitted actions.
Validate whether this model is sufficient for the intended first deployment and applicable obligations.
Clinical assurance
The owner has hospital domain knowledge.
GP-specific workflows still need review with actual GP users.
Keep assumptions separate from validated requirements.
Clinical deployment needs evidence concerning:
- Hazards.
- Mitigations.
- Usability.
- Data integrity.
- Security.
- Privacy.
- Operations.
- Applicable regulatory responsibilities.
Document 6 — Authentication, badges and roaming sessions
Suggested path: docs/identity-access.md
Account models
Support:
- Zantrix-managed staff accounts.
- Federation with an institution's identity provider through standard protocols.
Microsoft Entra ID was an example, not a mandatory selected product.
Do not interpret Zantrix-managed accounts as a decision to invent a custom password-security implementation.
Exact provider and protocols remain open.
Local and remote access
The owner's preference is:
Trusted on-site workstations
Allow:
- Username and password.
- A suitable employee badge.
Do not require MFA at every ordinary on-site sign-in.
Remote access
Require MFA, including working from home.
Trust classification
Still to design:
- What constitutes a trusted workstation.
- What constitutes on-site access.
- How VPN access is classified.
- Device trust.
- Network trust.
- Institutional identity assurance.
An IP address or VPN connection alone must not silently establish physical presence.
Badge technology
No badge type or reader has been selected.
A publicly readable badge number is not sufficient authentication assurance.
Assess:
- Verification mechanism.
- Copy resistance.
- Reader security.
- Lost-badge revocation.
- Recovery.
- Audit.
Daily and occasional verification
Accepted preference:
- First badge sign-in of the day also requires the user's password.
- Later badge sign-ins and unlocks may use the badge alone.
- Occasionally ask for the password again during the day.
- Do not make such checks too frequent.
Open details:
- Meaning of a day.
- Night shifts.
- Maximum time since verification.
- Frequency and bounds of occasional checks.
- Identity-provider compatibility.
- Recovery when a password is unavailable.
Random checks are not a substitute for a properly bounded authentication policy.
Switching users
On shared workstations:
- A staff member can switch to their own session using a badge.
- The previous user's session locks.
- Previous drafts remain associated with that user.
- Their patient information must not remain visible.
Roaming workspace
The owner wants it to feel as though the employee takes their computer with them.
Interpret this as a roaming Zantrix application workspace containing:
- Open patient records.
- Drafts.
- Clinical context.
- Relevant application state.
This is not a decision to implement a full remote desktop.
One active workspace
The owner explicitly requires:
A person must never be active in two places simultaneously.

For the primary application:
- One active staff workspace per user.
- Moving to another workstation locks the old one.
- Multiple patient workspaces inside that active session are allowed.
- The server rejects stale-session operations.
- Reconnection must not allow old writes to overwrite newer work.
The interaction with disconnected emergency readers remains open. A global guarantee cannot simply be assumed during network partitions.
Deliberate locking
Presenting the badge can immediately lock the workstation.
Do not depend on detecting that a contactless badge has left the area.
Inactivity behavior
Accepted timings:
Inactivity	Behavior
Before five minutes	Normal session unless otherwise locked
At five minutes	Hide all patient information behind a screen with a two-minute countdown
During countdown	A click returns to the session without authentication
At seven minutes total	Actually lock the session


After actual locking, authentication is required under the applicable sign-in policy.
The first screen is a privacy screen, not an authenticated lock.
Its protection is limited because another person could dismiss it.
Review the policy against the threat model and applicable deployment requirements before implementation.
Sensitive administration
Require reauthentication for high-impact administrative operations, including:
- Granting permissions.
- Installing modules.
Do not add these prompts indiscriminately to normal clinical work.
Open details include:
- Which actions are protected.
- Authentication strength.
- Verification freshness.
- MFA requirements for particular operations.
- Audit.
The owner's preference does not waive legally or clinically required checks.
Document 7 — Authorization, support and audit
Suggested path: docs/authorization.md
Basic model
Use function profiles as the baseline.
Allow:
- Standard Zantrix profiles.
- Institution-defined profiles.
- Multiple profiles per person.
- Location-scoped assignments.
- Individual additional permissions.
Examples such as GP, assistant and practice administrator are illustrative, not a finalized role catalog.
Individual additions
Individual extra rights are:
- Temporary by default.
- Automatically expired.
- Audited.
Permanent additions are possible with:
- An explicit choice.
- A recorded reason.
Effective permissions must be understandable to administrators:
- What is granted.
- Where it came from.
- Where it applies.
- When it expires.
- Who granted it.
Custom profiles
Institutions must be able to create profiles reflecting their own organization.
Modules expose supported permissions.
Custom profiles cannot disable fundamental platform protections.
Multiple profiles and location scope
One person can have multiple profiles.
Different assignments can apply at different locations.
An extra profile does not automatically remove a patient-specific restriction.
Explicit restrictions
An explicit restriction takes precedence over an allowance.
Only specifically designated restrictions can be overridden through the authorized emergency procedure.
The exact policy evaluation model remains to be designed.
Four-eyes principle
Dual approval for sensitive changes is:
- Optional.
- Configurable.
- Disabled by default.
When it is disabled, the normal requirements still apply:
- Appropriate permissions.
- Reauthentication where required.
- Audit.
Temporary staff
Temporary staff and locums have:
- Access start date.
- Access end date.
After expiry:
- Access ends automatically.
- Active access/sessions must be terminated appropriately.
- Historical clinical authorship remains.
Authorized staff can explicitly extend the period.
Revocation
Support immediate online revocation of:
- Access.
- Active sessions.
Distinguish:
- Blocking a badge.
- Disabling the complete account.
- Removing particular permissions.
Immediate revocation across an unreachable emergency reader cannot be guaranteed without a dedicated design.
Least privilege
Access is based on actual work need.
Technical administration does not automatically authorize patient-record access.
This also applies to Zantrix hosting and support personnel.
Do not grant access merely because someone manages servers or modules.
Support access
The institution may grant Zantrix support temporary patient-record access.
Requirements:
- Explicit institutional consent.
- Named support person.
- Defined purpose.
- Limited scope.
- End time.
- Revocation.
- Audit.
No consent means no application-level dossier access.
Infrastructure access to databases and backups requires separate safeguards.
Audit oversight
Provide an audit overview for specifically authorized personnel.
Include relevant information about:
- Actor.
- Time.
- Patient record.
- Action.
- Available care context.
- Explicit reason where required.
- Support access.
- Break-glass use.
Ordinary administrators do not automatically get this overview.
Audit-overview access is itself logged.
Break-glass
Allow justified emergency access within a defined scope.
Do not make every legitimate operational exception an emergency.
